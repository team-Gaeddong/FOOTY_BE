# FOOTY API 구현 워크플로

입력: GitHub 이슈 번호와 Notion 기능 이름. 둘 중 하나라도 없으면 먼저 요청한다.

## 0. 시작 전 확인 (건너뛰지 않는다)

1. `AGENTS.md`와 `docs/harness/decisions.md`를 읽는다.
2. 이번 작업에 필요한 미결정 항목을 표시한다. 대부분의 API는 최소한 다음이 필요하다.
   - D-01 계층 구조, D-02 패키지, D-03 응답 형식, D-04 에러 형식, D-05 인증 방식, D-06 DB·JPA, D-07 URL 규칙
   - D-09 미결정 상태의 테스트 기준은 AGENTS.md를 따른다. 테스트 의무 정책만 미결정이라는 이유로 독립 작업까지 중단하지 않는다.
3. 필요한 항목 중 `미결정`이 하나라도 있으면 **그 결정에 의존하는 코드를 쓰지 않는다.** 아래 형식으로 필요한 결정을 요청하고 독립 작업은 계속한다.

```
[결정 필요] D-03 응답 형식
- 이번 작업에서 필요한 이유: 회원가입 성공 응답 본문을 정해야 함
- decisions.md의 제안: (제안 요약)
- 선택지: A … / B …
```

## 1. 요구사항 정리

`docs/harness/sources.md`의 원본 확인 범위를 확인한다. `references/feature-map.md`에서 기능 행을 찾고, 다음 네 가지를 적어 사람에게 확인받는다(1차 스크럼 회고록 프롬프트 설계 규칙).

- 입력: 경로 변수, 쿼리, 요청 본문 필드와 검증 조건
- 출력: 상태 코드와 응답 필드
- 예외 상황: 권한 없음, 대상 없음, 중복, 상태 위반 등과 각 상태 코드
- 레퍼런스: 관련 Notion 기능 설명, ERD 테이블·컬럼, 선행 API

Notion 기능 설명은 대부분 한 줄이다. 설명에 없는 규칙(예: 18명 초과 시 후보 선정 기준)을 지어내지 말고 질문으로 남긴다.

## 2. 스키마 대조

- 필요한 테이블·컬럼을 `docs/erd/footy_erd.sql`에서 찾는다.
- 기능에 필요한 데이터가 ERD에 없으면(예: 경기 결과 점수) 구현을 멈추고 `decisions.md` 형식으로 보고한다. 엔티티에 임의 컬럼을 추가하지 않는다.
- 엔티티 필드명·NULL 여부·UNIQUE 제약은 DDL과 같아야 한다.

## 3. 브랜치

`footy-git-workflow` 스킬에 따라 `feature/{이슈번호}_{할일}` 브랜치를 만든다. base 브랜치가 미결정이면 확인한다.

## 4. 구현 순서

확정된 D-01 계층 구조를 따른다. 확정 전에는 이 단계로 오지 않는다. 각 단계가 끝날 때마다 `./gradlew compileJava`로 확인한다.

1. 엔티티·리포지토리 (스키마와 일치)
2. 요청·응답 DTO와 입력 검증
3. 서비스: 도메인 규칙과 권한 확인(파티장 전용 동작 등)
4. 컨트롤러: URL, 상태 코드, 응답 형식(D-03), 에러 형식(D-04)
5. 테스트: 정상·예외 경로의 새 테스트를 권장한다. D-09 확정 전에는 기존 테스트 실행을 필수로 하며, 사용자·이슈에서 요구한 테스트는 반드시 작성한다. 테스트가 없는 경로와 남은 위험을 보고한다.

## 5. 검증

```bash
./scripts/harness/check.sh --mode baseline  # 커밋 전: 빌드·기존 테스트
# 커밋 후, 확정된 PR base를 지정해 변경 검사
./scripts/harness/check.sh --base origin/main
```

위 `origin/main`은 명령 예시이며 D-10의 결정을 대신하지 않는다. 확정된 base로 바꾼다. 종료 코드 2(일부 검사)는 완료가 아니다. 실패하면 고친 뒤 다시 실행한다. 원인이 이번 변경 밖에 있으면 고치지 말고 출력과 함께 보고한다.

## 6. 커밋과 PR

- 커밋은 의미 단위로 나누고 `footy-git-workflow`의 형식을 따른다.
- PR 본문에 요구사항 표(입력·출력·예외·레퍼런스), 검증 출력, 결정 필요 항목을 넣는다.
- PR 작성 후 `footy-code-review` 스킬로 자체 점검을 한 번 돌리고 결과를 PR 코멘트 초안으로 정리한다. 자체 점검은 사람 승인을 대신하지 않는다.

- [ ] 기존 테스트를 실행했고, 사용자·이슈 또는 확정된 D-09가 요구한 테스트를 작성했다. 나머지 정상·예외 경로의 테스트 누락은 보고했다
